# Стилевые принципы Skadi

## Статус

Принятый базовый набор принципов для ближайших языковых решений.  
Дата последней сверки: 2026-07-30

## Главная цель

Синтаксис Skadi должен читаться без когнитивного напряжения.

Это не цель "сделать как можно короче".  
Это цель "сделать чтение плавным".

Skadi должен учить не только записи алгоритма, но и системному мышлению:
владению, времени жизни, стоимости копирования, размещению данных, блокировкам
и завершению ресурсов. Машинная модель не должна исчезать, но её не следует
объяснять пользователю через случайную сложность указателей и ручных ритуалов.

## Где заканчивается язык

Граница Skadi не совпадает с границей parser grammar.

Официальная среда делится на четыре слоя:

1. **Language Core** - значения, функции, control flow, ошибки и ownership.
2. **Systems Core** - `Memory`, `Task`, `Channel`, `Time`, `Interrupt` и общий
   lifecycle ресурсов.
3. **Domain Core** - тщательно отобранные поверхности вроде Canvas, I/O и
   filesystem, которые сохраняют единые правила Skadi.
4. **Platform Backends** - Win32, POSIX, embedded/RTOS и конкретные устройства.

Внешняя библиотека начинается не там, где заканчивается синтаксис, а там, где
проект больше не гарантирует единую философию API, diagnostics, ownership,
ошибок и стоимости операций.

Canvas является принятым примером Domain Core. Его примитивы не обязаны быть
новыми синтаксическими формами, но их контракт проектируется вместе с языком.
Полный GUI toolkit, game engine или media framework остаётся библиотечным слоем.

## Базовое правило чтения

Предпочитать формы, которые читаются как техническая проза, даже если они длиннее.

Пример:

- `returns` предпочтительнее символического `->`

## Эталон стиля записи

Канонический стиль для сверки:

- `examples/example_meteostation.skd`

Любое новое синтаксическое предложение нужно проверять на совместимость с этим стилем до принятия.
Сам образец намеренно компактный и не завязан на embedded-слои, чтобы его можно
было читать как showcase стабильной основы. Systems- и domain-возможности
проверяются отдельными актуальными examples и benchmarks.

## Позиционирование языка

Skadi нацелен на системное программирование с привычными возможностями C-класса, но с более читаемым синтаксисом.

Практическая интерпретация:

- сохранять низкоуровневую и системную полезность;
- сохранять гибкость по target/toolchain;
- уменьшать символический шум там, где он мешает чтению.

## Правило каноничности

Для каждой фичи должен быть один канонический способ записи.

Нужно избегать параллельных стилей для одной и той же операции, если нет критической технической причины.

## Правило снижения шума

Нужно уменьшать punctuation-heavy формы там, где keyword-based форма читается яснее.

Примеры принятого направления:

- `returns` вместо `->`
- keyword-based конструкции там, где они улучшают мгновенное понимание
- кандидат на прозаический цикл: `iterate collection as item`

## Дисциплина области видимости

Не расширять синтаксическую поверхность, если этого же результата можно достичь
обычным вызовом или типом без потери ясности.

Основной пользовательский поток:

- писать system-style code;
- легко его читать;
- предсказуемо компилировать.

## `when / is`

`when / is` - каноническая Skadi-форма `switch / case`, а не альтернативное
написание `if`.

Целевые инварианты:

- выражение `when` вычисляется один раз;
- `is` не имеет implicit fallthrough;
- duplicate cases являются ошибкой;
- case type согласуется с типом разбираемого значения;
- для `label`/`tag` static analyzer проверяет полноту вариантов;
- `else` требуется, если разбор не доказан как полный.

Расширять `when` pattern matching следует только после закрепления этих простых
инвариантов.

## Обучение управлению ресурсами

Каноническая учебная последовательность:

```text
values and scopes
-> explicit errors
-> resource lifecycle and close
-> view / direct / move
-> Memory
-> Task / Channel
-> Interrupt and embedded
-> C FFI
```

Диагностика и TUI должны уметь объяснять историю значения: где оно создано,
скопировано, заимствовано, перемещено и закрыто; где операция может выделять
память или блокировать выполнение.

## Фильтр принятия нового синтаксиса

Новое предложение должно проходить все проверки:

1. Его легче читать без напряжения.
2. Оно не вносит неоднозначность в parsing.
3. Оно согласуется со стилем из `examples/example_meteostation.skd`.
4. Оно не создаёт вторую конкурирующую форму для той же фичи.
5. Его стоимость, ошибки и lifecycle можно сделать видимыми.
6. Оно естественно сочетается с ownership, Memory и Task/Channel.
7. Domain Core допускает несколько backend без изменения пользовательской
   модели.

Статус идеи проходит явный цикл:

```text
draft -> experimental -> canonical
                   \-> rejected
```

Удаление неудачной experimental-идеи является нормальным результатом проверки,
а не нарушением совместимости.

## Кандидаты на сокращение

Следующие направления не должны незаметно расширять основную поверхность:

- `fixed`/`const` не конкурируют с рабочим `constant`;
- `allow drop` у Memory не означает automatic reclamation; `drop oldest`
  относится к явным bounded containers вроде `Ring`, `Pool` или `Channel`;
- generic dimensional algebra не следует автоматически из наличия
  `Duration`, `ByteSize` и `Angle`;
- Canvas Core не включает полный GUI/media/game framework;
- Matrix/SIMD/swizzle API относится к math/domain layer, а не к grammar;
- новые `on event`-подобные формы не добавляются до появления сценария,
  который нельзя ясно выразить через существующие Task/Channel/Interrupt.
